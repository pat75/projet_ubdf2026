TRANSFERT DE LA BASE MYSQL — ancienne prod -> O2switch (ultra-book.pro)
=========================================================================
Script : ./deploy/transfert-base.sh   (depuis la racine du projet, sur le Mac)
Base source : db_ultra_book_2019 (ancien serveur 163.172.103.215), format
legacy : memes tables que la copie locale ub2020.
Base cible  : sc4tapa2662_ultra-book-prod (O2switch), schema 2026.
UNE SEULE BASE : les tables legacy (inc_*, ub2_*, bn_*, df2_*, nl_*,
wp_import) sont importees DANS sc4tapa2662_ultra-book-prod, a cote des
tables 2026 (aucune collision de nom), puis converties vers ces tables.
Avant CHAQUE modification de cette base : sauvegarde horodatee en gzip,
verifiee, dans ~/backups_deploy/ (arret si elle est invalide).


PRINCIPE
--------
0) EXPORTER   mysqldump a la main sur l'ancien serveur (etape 1 ci-dessous).
1) RECUPERER  O2switch tire le dump de l'ancien serveur (rsync, mot de
              passe) -> ~/ultra-book.pro/data_sql/   (hors public/, exclu
              du deploiement et de git).
2) ANALYSER   sauvegarde, puis import des tables legacy dans
              sc4tapa2662_ultra-book-prod, connexion DB_LEGACY_* dans
              .env.prod (meme base, latin1), puis analyse : integrite,
              encodage, tables non reprises, troncatures par champ. Les
              tables 2026 ne sont pas touchees.
3) CONVERTIR  apres lecture du rapport et confirmation : sauvegarde de la
              prod, maintenance, reprise ubdf:migrate-legacy --tous vers
              le schema 2026, fin de maintenance, rapport final.
4) SUPPRIMER  a la toute fin : sauvegarde, puis retrait du dump et des
              tables legacy (elles servent aussi a « organiser » les
              images : les garder jusque-la).

Meme logique que le transfert des images (tutoriel_transfert_data_image.txt) :
reglages OLD_* communs, port 2083, screen, journal dans deploy/logs/.


AVANT DE COMMENCER
------------------
a) deploy/deploy.config :
      OLD_SSH_USER / OLD_SSH_HOST / OLD_SSH_PORT   communs avec les images
                                                   (OLD_SSH_PORT="2083")
      OLD_DUMP   chemin du dump sur l'ancien serveur, ex.
                 /home/adminpat/db_ultra_book_2019_2026-10-02.sql.gz
      DATA_SQL   data_sql (dossier de reception)
b) Liaison O2switch -> ancien serveur :
      ./deploy/transfert-base.sh diagnostic     (attendu : « reseau OK »)
   En cas de blocage : tutoriel_transfert_data_image.txt, section
   BLOCAGE SSH SORTANT (port 2083, CSF).
c) Le code doit etre deploye : ubdf:prod:analyser-legacy, et la reprise
   des abonnes / le detail des troncatures font partie du code.


ETAPE 1 — EXPORTER (a la main, sur l'ancien serveur)
----------------------------------------------------
Connexion SSH a l'ancien serveur, dans un dossier avec quelques Go libres :

   mysqldump -u ultrabook2019 -p \
     --default-character-set=latin1 \
     --hex-blob \
     --quick \
     --no-tablespaces \
     --skip-lock-tables \
     db_ultra_book_2019 \
     | gzip > db_ultra_book_2019_$(date +%F).sql.gz

- -p sans valeur : le mot de passe est DEMANDE. Ne pas ecrire -pMOTDEPASSE
  (il resterait dans l'historique et la liste des processus).
- --default-character-set=latin1 : INDISPENSABLE. Les tables sont
  declarees latin1 mais contiennent de l'UTF-8 brut ; latin1 les exporte
  tels quels. Un export phpMyAdmin les reencode et peut abimer des accents.
- --skip-lock-tables : l'utilisateur de l'ancien site n'a pas le droit
  LOCK TABLES (erreur 1044 sinon). Sans verrou, le dump n'est coherent que
  si personne n'ecrit : le lancer la nuit, ou fermer l'ancien site.
- --hex-blob : champs binaires intacts. --quick : ligne a ligne.

Verifier :
   ls -lh db_ultra_book_2019_*.sql.gz
   zcat db_ultra_book_2019_*.sql.gz | tail -1     -> « -- Dump completed on ... »

Si le nom du fichier change (autre date), mettre a jour OLD_DUMP dans
deploy.config, ou passer --chemin= a « recuperer ».


ETAPE 2 — RECUPERER
-------------------
   ./deploy/transfert-base.sh recuperer
   -> confirmation, puis mot de passe de l'ANCIEN serveur (SSH adminpat).

Dans « screen » sur O2switch : continue si le Mac se met en veille.
   Ctrl-A puis D                         se detacher
   ./deploy/transfert-base.sh suivre     revenir voir la progression
A la fin : code rsync (0 = complet), gzip intact, « Dump completed ».
Relancer recuperer reprend un fichier coupe.

Controle a tout moment :
   ./deploy/transfert-base.sh verifier
   -> taille, gzip intact, « Dump completed », empreinte.


ETAPE 3 — ANALYSER (les tables 2026 ne sont pas touchees)
---------------------------------------------------------
   ./deploy/transfert-base.sh analyser

1) verifie le dump (arret s'il est absent ou incomplet) ;
2) controle les tables du dump : seules les tables legacy (inc_*, ub2_*,
   bn_*, df2_*, nl_*, wp_import) sont acceptees ; une autre (users,
   media...) arrete tout, pour ne jamais ecraser une table 2026 ;
3) SAUVEGARDE horodatee de sc4tapa2662_ultra-book-prod :
      ~/backups_deploy/base-<date>-avant-import-legacy.sql.gz
   verifiee (gzip, taille) ; arret si elle est invalide ;
4) importe le dump dans sc4tapa2662_ultra-book-prod (latin1, comme
   l'export) ; relancable : le dump recree ses propres tables ;
5) propose d'ajouter DB_LEGACY_* a .env.prod (confirmation) : meme base,
   connexion en latin1, protegee en ecriture par l'application ;
6) lance l'analyse et ecrit le rapport :
      storage/logs/analyse-legacy-<date>.txt   (serveur)
      deploy/logs/analyse-legacy-<date>.txt    (copie sur le Mac)

Le rapport (lignes « ! » = points a lire) :
   1) INTEGRITE    lignes par table, tables absentes, comptes vivants /
                   supprimes (non repris)
   2) ENCODAGE     valeurs doublement encodees (« Ã© ») ou abimees, par
                   table.colonne, avec des id
   3) NON REPRISES tables que la reprise ne lit pas, et leur nombre de lignes
   4) TRONCATURES  valeurs plus longues que la colonne 2026, par
                   table.colonne -> table.colonne, avec des id

Resultat sur ub2020 (copie 2020, pour reference) : 1 description
suspecte (ub2_gal_img.img_desc, id 562678), 2 telephones trop longs
(inc_user.us_telephone -> users.phone, id 11219 et 14003).

A SAVOIR : bn_ultranews_art_tab_default (corps des actualites d'avant
2015, ancien modele) n'est pas reprise. Sur ub2020 : 62 682 actualites de
18 874 comptes vivants arriveraient SANS texte. Beaucoup sont des textes
par defaut (« Vous pouvez bien sur la modifier... »), mais pas toutes.
A trancher avant la conversion (la reprise peut etre etendue).


ETAPE 4 — CONVERTIR
-------------------
   ./deploy/transfert-base.sh convertir

1) refuse de partir sans analyse du MEME dump (empreinte comparee) ;
   rappelle les points « ! » de l'analyse ;
2) rappelle les tables videes / gardees ; taper CONVERTIR pour lancer ;
3) SAUVEGARDE horodatee de sc4tapa2662_ultra-book-prod :
      ~/backups_deploy/base-<date>-avant-reprise.sql.gz
   verifiee (gzip, taille) ; arret si elle est invalide ;
4) dans « screen » : maintenance, php artisan migrate --force,
   ubdf:migrate-legacy --tous --fresh --skip-files, cache:clear, fin de
   maintenance, rapport. Duree : 1 h 30 a 2 h (rechiffrement de ~60 000
   mots de passe).
   En cas d'echec : le site RESTE EN MAINTENANCE ; relancer la reprise a
   partir du dernier us_id affiche (--depuis=), ou restaurer la sauvegarde.

Rapport final :
   ./deploy/transfert-base.sh rapport
   -> volumes repris, valeurs coupees par table.colonne (exemples d'id
      legacy), logins sans conversion possible, duree. Copie dans
      deploy/logs/.

Les images ne sont pas concernees (--skip-files) : voir
tutoriel_transfert_data_image.txt (recuperer, organiser).

SUIVI
-----
   ./deploy/transfert-base.sh etat
   -> dump recu, derniere analyse, dernieres sauvegardes, sessions
      screen en cours, espace disque, tables legacy dans la base.
Journal de chaque lancement : deploy/logs/transfert-base-<date>-<commande>.log


REVENIR EN ARRIERE
------------------
Chaque etape qui modifie la base laisse sa sauvegarde horodatee :
   base-<date>-avant-import-legacy.sql.gz      (analyser)
   base-<date>-avant-reprise.sql.gz            (convertir)
   base-<date>-avant-suppression-legacy.sql.gz (supprimer)
Restaurer la bonne :

   ./deploy/ssh-prod.sh
   puis, sur le serveur :
   gunzip -c ~/backups_deploy/base-<date>-<etape>.sql.gz | mysql -u sc4tapa2662_ultra-book-prod -p sc4tapa2662_ultra-book-prod
   (mot de passe : DB_PASSWORD de .env.prod)
   php artisan cache:clear


A LA FIN : SUPPRIMER
--------------------
Quand la reprise est validee ET que « organiser » a tourne sur toutes les
lettres (il lit les tables legacy pour convertir les logins) :

   ./deploy/transfert-base.sh supprimer      (taper SUPPRIMER)

Sauvegarde horodatee, puis supprime les tables legacy de
sc4tapa2662_ultra-book-prod (les tables 2026 restent), le dump de
data_sql/ et DB_LEGACY_* de .env.prod (renvoye au serveur).
